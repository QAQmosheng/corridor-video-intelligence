# 新视频算法设计说明

## 1. 设计目标与边界

系统按“视觉事实、时空状态、业务事件”三层解耦。模型或规则只输出事实；`EventEngine` 是唯一可生成事件的组件；WeKnora 只消费事件并执行知识检索和处置编排。这样更换检测模型不会改变事件语义，也不会让视觉大模型越权决定处置动作。

本原型没有复用旧系统算法。当前的可解释视觉内核用于验证数据流与状态机，未来的新 ONNX 模型是一个受控替换点。

## 2. 每帧处理链路

```text
视频帧
  → 单摄像头动态基准
  → 抗噪差异比例 + 连续帧确认
  → 稳定差异门控
  → 新语义检测器
  → 质心轨迹关联
  → 人员 / 非人员分流
  → 廊段级会话状态机
  → JSON Schema 事件
  → SQLite Outbox
```

### 2.1 动态基准

每个 `camera_id` 拥有独立基准、版本和状态。像素差先缩放到 320×180 灰度图计算，以 `pixel_threshold` 形成变化掩码，再用 `changed_area_ratio` 与 `stable_confirm_frames` 过滤压缩噪声和瞬时遮挡。

变化比例超过 `global_change_ratio` 视为强光、遮挡或镜头移动，基准失效，不触发自动遗留物结论。人员会话建立后，整个廊段所有摄像头的基准被冻结；会话关闭后才允许继续学习。

### 2.2 原型语义层

当前 `NativeVisionPipeline` 使用 HSV 色彩、连通域、形状比例和画面位置完成确定性候选分类：

语义分类只处理“当前帧相对基准图发生变化”的掩膜区域，不再对整张画面扫描；顶部固定水印区域默认屏蔽。无法明确分类的变化区域标记为未知并忽略，禁止兜底登记成可携带物品。

- 纵向人体候选：按上部区域红色占比给出安全帽外观状态；红色同时覆盖 HSV 色相环的低端和高端区间；
- 多人靠近导致轮廓合并时可使用红色安全帽作为人员组提示，但安全帽状态保持 `unknown`，禁止用一个合并框推断所有人均正确佩戴；
- 对本项目统一使用红色安全帽的画面，优先以每顶紧凑红色安全帽为定位锚点向下生成独立人员框，避免多人及背景变化连接成覆盖管道的大框；
- 颜色规则未观察到红帽时不能据此断言“人员”或“未佩戴”；仅由长宽比得到的 `unknown` 人员候选默认不输出，未戴帽报警必须由后续 ONNX/VLM 人员与 PPE 识别器明确确认；
- 横向可携带物：登记为 `portable_object`；
- 红橙高饱和区域：火焰候选；
- 画面下部蓝色横向区域：积水候选；
- 人员与物品使用最近质心做短时轨迹关联。

这套规则便于演示、测试和现场阈值标定，但不是生产识别器。生产化时使用本项目独立采集的管廊数据训练多任务检测器，建议输出 `person / helmet / no_helmet / portable_object / animal / fire / smoke / water_region`，以 ONNX Runtime 或 TensorRT 实现新的 `semantic_candidates()`；严禁把旧权重作为临时替代。

## 3. 廊段状态机

状态依次为：

```text
idle → active → exit_pending → inspecting → closed
                          ↘ manual_review
```

- `active`：任一关联相机发现人员，生成唯一会话并冻结全部基准；
- `exit_pending`：当前帧无人，但仍在最大跨镜时间和离场确认窗口；
- `inspecting`：全部相机健康、最近均无人员，开始验证物品独处持续时间；
- `closed`：物品被带走，或已为持续物品生成一次事件；
- `manual_review`：任一相机离线、基准失效或全局画面突变，禁止自动确认。

遗留物必须同时满足：会话中新增、整个廊段人员已离开、离场后仍在原相机持续存在。候选在其所在相机消失后立即移除。幂等键为 `corridor_session_id + camera_id + object_track_id`。

## 4. 人员和视觉复核

正确佩戴安全帽仅输出 `worker_detected` 外观状态，不能证明身份或作业授权；未佩戴连续达到阈值后输出 `person_intrusion`。

火烟和积水候选才会进入视觉大模型复核。复核响应标签必须在白名单内；积水深度无法从单目可靠得到，始终禁止推断。复核不可用时输出 `visual_review_required`，不把候选伪装成已确认事实。

## 4.1 报警生命周期与去重

逐帧检测结果不会直接等价为逐帧报警。事件引擎按“摄像头 + 事件类型 + 原因 + 空间重叠”关联同一异常，状态依次为 `candidate → active → closed`：

- 普通候选连续命中 `lifecycle.confirm_frames` 后只创建一次事件；
- 同类别目标框 IoU 达到 `spatial_iou_threshold` 时视为同一持续异常；
- `active` 期间只更新最后观察时间，不重复写入 Outbox；
- 连续 `lifecycle.clear_frames` 未命中且消失时间达到 `clear_seconds` 后关闭，之后重新出现才能建立新事件；
- 遗留物已经经过人员离场和持续时间确认，作业人员状态也无需重复等待，因此配置为立即类型，但仍受生命周期抑制重复报警；
- `events.cooldown_seconds` 保留为进程重启、边界抖动等情况下的第二道保护。

## 5. 生产化验收建议

1. 建立独立数据集，按摄像头、昼夜、粉尘、反光、遮挡划分，禁止相邻帧跨训练集和测试集泄漏；
2. 单模型验收 mAP、召回率与每类混淆矩阵，同时以“每摄像头每天误报数”验收业务效果；
3. 重点回放人员跨镜盲区、物品被带走、摄像头掉线、镜头移动、强光突变场景；
4. 先影子运行，只记录新旧结果差异；满足门槛后再让新模块成为正式事件源；
5. 模型版本、阈值版本、基准版本和事件 Schema 版本必须随事件保存，支持完整追溯。
